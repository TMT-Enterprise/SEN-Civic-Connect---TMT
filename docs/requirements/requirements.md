# Requirements and Acceptance Criteria

| ID | Requirement Type | Description | Source | Acceptance Criteria |
|---|---|---|---|---|
| FR-001 | Functional | The system shall allow registration for new users using a unique email address. | Requester | - Registration succeeds if the user input is not already stored in the system<br>- When registration fails, an error message is shown<br>(Rodriguez, 2026) |
| FR-002 | Functional | The system shall allow registered users to log in (authenticate) using their email and password. | Requester | - Login succeeds with valid email and password<br>- Login fails with incorrect password; error message shown<br>(Rodriguez, 2026) |
| NF-001 | Non-functional | The system must be protected from unauthorised access; access shall be restricted to authenticated users (Khomenko, 2026). | Requester & Security | - Unauthenticated users cannot access authenticated functionality<br>- A user cannot log in with failed registration details<br>(Rodriguez, 2026) |
| NF-002 | Non-functional | Role-based access shall be enforced for requesters, staff, admin (staff), and management. | Requesters & Staff & Management | - A requester shall not be authorized to access staff-only or management-only functionality<br>- Staff shall not be authorized to access requester, admin-only, or management-only functionality<br>- Admins shall not be authorized to access management-only functionality |
| NF-003 | Non-functional | The system shall store user passwords using a secure hashing mechanism. | Requesters & Staff & Management | - Password shall not be stored using plain text<br>- Hashing algorithm must be a one-way mechanism |
| FR-003 | Functional | The system shall allow an authenticated user to submit a new service request containing their name, contact details, category, and short description of the request. | Requester | - New service request form auto-fills personal information based on the logged-in profile<br>- The category is a controlled list with the following options: Facility faults, Damaged equipment, Security concerns, IT support, Maintenance issues, Lost property and Other<br>- A submitted request succeeds with valid user input<br>- A submitted request fails with invalid input; error message shown |
| FR-004 | Functional | The system shall create a unique identifier for every successfully submitted service request. | Staff & Management | - Identifier needs to be unique; no duplicates allowed |
| FR-005 | Functional | The system shall display the current status of a submitted request to its requester. | Requester | - Status levels to be seen by the requester include Submitted, Assigned, In Progress, Resolved, or Closed<br>- Overdue is a system-generated state when the due date passes before closure |
| FR-006 | Functional | The system shall send notifications via email to the requester informing them when their request has moved to a new status level. | Requester | - The email contains the request ID<br>- The email contains the new status<br>- The email is sent to the email address associated with the requester's account<br>- No email is sent when the status has not been changed<br>- The email shall not allow the requester to modify the request through the email<br>- The email shall be sent within 60 seconds of a status update (Rodriguez, 2026) |
| FR-007 | Functional | The system shall allow the requester to view a history of their previous requests. | Requester | - Access to request history includes all information submitted by the requester and timestamps of when it was completed<br>- Requesters should not be able to see requests from other requesters |
| FR-008 | Functional | The system shall allow authenticated admins to view and assign new incoming service requests from authenticated requesters. | Staff | - Only staff who are admins shall be allowed to view unassigned service requests<br>- Admins assign service requests to normal staff (The Indeed Editorial Team, 2026)<br>- The admin may see all the request details submitted by the requester<br>- Admins may set a due date and time for when the request needs to be completed by<br>- Minimum time of completion is 1 day (24 hours) (Gupta, 2020) |
| FR-009 | Functional | The system shall allow staff to view, search, and filter service requests by request ID, status, due date, category, and assigned staff member. | Staff | - Only an admin may view all service requests and filter using (un)assigned staff<br>- Staff may only view their own service requests and may not be able to see other staff's service requests<br>- Search is case-insensitive<br>- Partial matches are included in results<br>- An empty search query shows all service requests<br>- Zero-result state shows helpful messaging<br>(Rodriguez, 2026) |
| FR-010 | Functional | The system shall allow normal staff members to accept or reject assigned service requests. | Staff | - Status of an accepted service request will update to "Assigned"<br>- Status of a rejected service request must remain as "Submitted"<br>- A rejected service request shall be recorded<br>- Rejected service requests return to the admin's view of unassigned requests |
| FR-011 | Functional | The system shall allow staff to update the request status of a service. | Staff | - A confirmation message shall be shown when staff changes the status level of a request<br>- Staff shall not be able to modify any additional information in the service request; controlled updates<br>- Staff may not be able to move the service request status backwards or skip levels; sequential and forward moving<br>- Any staff member is authorized to move a service request to "Closed"; completing the service |
| FR-012 | Functional | The system shall generate a state called "Overdue" when the assigned due date passes before closure of a service request. | Staff | - "Overdue" shall replace and override the current status<br>- Given a request has a due date of 13:00, when 13:00 passes and the request is not yet closed, the system will mark the service request as "Overdue" |
| FR-013 | Functional | The system shall record each change request with the request ID, staff responsible, and timestamp. The system shall record rejection and resolution comments with associated requests. | Staff & Management | - Only admin and management may see the audit trail of all staff<br>- Staff shall be required to provide a short description of the work they completed before moving the service request to a "Closed" status<br>- An error message shall be provided if the short description has invalid input |
| FR-014 | Functional | The system shall provide management with a dashboard view of statistical data (such as totals, averages, and timestamps) of service activity. | Management | - Management shall see real-time data on the dashboard after refreshing the page<br>- Counts and data shall correspond to the underlying service request records |
| FR-015 | Functional | The system shall allow management to search and filter management reporting information across all service requests by due date, status, category, timestamps, and assigned staff. | Management | *(acceptance criteria to be finalised)* |
| FR-016 | Functional | The system shall allow management to view the complete lifecycle history of a service request. | Management | - Each lifecycle displays a timestamp of each status and the responsible staff member of a service request<br>- The timestamp of a status not reached yet will default to "n/a" |
| NF-004 | Non-functional | At least 95% of staff and management shall be able to complete the defined core service-management tasks after one hour of training (Sommerville, 2015). | Staff & Management | - Core tasks include: find and filter requests, assign a request, accept/reject a request, view audit history<br>- After training, the average error when coordinating service request work should not exceed 5% (Sommerville, 2015; Khomenko, 2026) |
| NF-005 | Non-functional | At least 95% of requesters shall take no more than five minutes to fill in a service request form. | Requesters | *(acceptance criteria to be finalised)* |
| NF-006 | Non-functional | Search results appear in under 3 seconds (Larmier, 2026). | Requesters & Staff & Management | - At least 95% of search operations shall return search results within 3 seconds |
| NF-007 | Non-functional | The system shall provide at least 90% availability to requesters, staff, and management during operating hours, excluding scheduled maintenance (IBM, 2025). | Requesters & Staff & Management | *(acceptance criteria to be finalised)* |

**Note:** FR-015, NF-005 and NF-007 are missing finalised acceptance criteria in the source
document.
