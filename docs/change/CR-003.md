# CR-002: Developer-based branching strategy, hotfix isolation, and role-restricted governance

| Field | Detail |
|---|---|
| Requested by | GitHub governance lead |
| Date | 22 September 2026 |
| Requested change | Adopt (1) a persistent per-developer branching model, each team
member maintains one ongoing branch, pulls from main before new work, resolves conflicts
locally, and merges via reviewed PR; (2) an isolated hotfix protocol, a critical bug on main is
fixed on a dedicated temporary branch while main is frozen to other merges, enforced by a
required CI check; (3) role-restricted administration, Admin-level repository and project
access (branch rules, secrets, collaborator management, board automations) reserved to the
GitHub lead, Write access for the other two members; (4) an expanded CI pipeline enforcing the
A2 Task 4 build/test/lint/audit gate rules. |
| Reason / expected value | A three-person team incurs disproportionate coordination overhead
from creating and retiring a branch per micro-task; a small, stable set of persistent branches
reduces that overhead while still funnelling every change through a reviewed PR into protected
main, a simplified variant of the persistent-branch approach described for small teams
(Driessen, 2010). Reserving destructive/administrative permissions to one person reduces the
risk of an accidental or unreviewed change to governance controls, consistent with the
least-privilege principle already applied to CivicConnect's own access-control requirement
(NF-002). |
| Requirements affected | None functional; governance/process only. |
| Architecture/design affected | None. |
| UI/API/data affected | None. |
| Security/privacy impact | Reduces risk surface: only one account can alter branch
protection, secrets, or collaborator access. |
| Quality/testing impact | CI now enforces build, test, and critical-vulnerability gates on
every PR, and blocks merges during an active hotfix freeze. |
| Scope impact | None to product scope; adds two GitHub Actions workflows and one CODEOWNERS
file to the repository. |
| Schedule/resource impact | Low. Setup is a single session; ongoing overhead is the discipline
of frequent pulls from main (already part of the proposed strategy). |
| Cost impact | None (GitHub Actions minutes are free at this usage level for a private
student repo on the free tier). |
| Risk impact | The documented risk of persistent, longer-lived branches is delayed
integration: divergence increases the size and difficulty of eventual merges, and can
discourage refactoring of shared code (Fowler, 2020). Contingency measures below are adopted
specifically to counteract this. |
| Recommendation | ACCEPT, conditional on the contingency measures being followed, not just
adopted in name. |
| Approved by | *(two team members other than the requester to confirm here)* |
| Rationale | Matches team size and capability, technically enforces the stated hotfix rule
rather than relying on memory, and pairs the known risk of long-lived branches with concrete,
checkable mitigations rather than ignoring the trade-off. |

## Contingency plan for long-lived-branch risk
- Pull from main before starting each new piece of work, and again before opening a PR, not
  only when convenient (Fowler, 2020, identifies delayed integration, not branch persistence
  itself, as the actual source of risk).
- Open a PR (draft is fine) at least every few days per active piece of work, rather than
  holding everything until it feels "done," so review and CI catch integration problems early.
- Rebase onto main rather than merging main in, to keep history linear and conflicts visible
  at the point they're introduced, not buried in a later merge commit.
- CODEOWNERS and the existing frontend/backend split (per the Team Accountability table)
  keep each person working in mostly separate areas, reducing the odds of two branches
  silently touching the same code.
- The main-freeze check isolates the one genuinely dangerous convergence point, a hotfix
  landing on main, from colliding with three people's independent ongoing work.
