# CR-005: Placeholder for request title

| Field | Detail |
|---|---|
| Requested by | Tinyiko Siwele |
| Date | 11/10/2026 |
| Requested change | 

Revise the role-based access control model from three staff roles (Staff, Admin and Management) to two staff roles (Staff and Admin). Admin and Management shall be used interchangeably throughout the project documentation, as both represent the same role with identical permissions and functionality. Requesters remain a separate user type. |
| Reason / expected value | The original distinction between Admin and Management introduced unnecessary complexity because both roles have access to the same functionality. Consolidating them into a single Admin role simplifies authentication, authorisation, database design, API access control, UI navigation and testing while preserving the separation between normal staff and administrative responsibilities. |
| Requirements affected | NF-002: Update role-based access control to reflect Requester, Staff and Admin as the three distinct access groups, with Admin replacing the separate Management role. FR-008: Admins may view unassigned requests, assign requests to staff and set due dates. FR-009: Admins may view all requests and filter by assigned or unassigned staff, while normal staff may only view their own requests. FR-013: Admins may view the audit trail of all staff. FR-014: The Admin role shall have access to the management dashboard and service activity statistics. FR-015: Admins may search and filter management reporting information across all service requests. FR-016: Admins may view the complete lifecycle history of service requests. FR-004 and FR-013 may also use Admin in place of Management in their source and responsibility references where appropriate. FR-001, FR-002, NF-001 and NF-003 remain applicable to registration, authentication, access restriction and password security. |
| Architecture/design affected | The role-based access control design shall support Requester, Staff and Admin as distinct roles. The separate Management role and its permissions shall be removed. Admin and Management shall refer to the same authorisation level, with no separate Management permission set. Access to administrative and reporting functionality shall be controlled through role-based authorisation. |
| UI/API/data affected | UI: Provide role-appropriate navigation and functionality for Requesters, Staff and Admins. The Admin interface shall include administrative request assignment, reporting, dashboard and lifecycle-history functionality. API: Update authorisation rules and protected endpoints to recognise the Admin role instead of a separate Management role. Normal staff must remain restricted to their own assigned service requests and permitted status updates. Data: Update the employee-role structure and seed data to support Staff and Admin only. Remove the separate Management role and ensure existing role references are migrated or updated consistently. |
| Security/privacy impact | NF-001 and NF-002 must continue to prevent unauthorised access. Requesters must not access staff or administrative functionality. Staff must not access Admin-only functionality or other staff members' restricted requests. Admins may access the administrative and reporting functionality previously available to both Admin and Management. NF-003 remains unchanged: passwords must be stored using a secure one-way hashing mechanism.|
| Quality/testing impact | Update authentication and authorisation tests to verify access for Requester, Staff and Admin roles. Confirm that normal staff cannot access administrative request assignment, organisation-wide reporting, the staff audit trail or complete lifecycle-history functionality unless explicitly authorised by the revised requirements. Verify that Admin users can access the functions previously assigned to both Admin and Management. |
| Scope impact | Minor scope and documentation changes. The change simplifies the existing role model without introducing new functional capabilities. |
| Schedule/resource impact | Minimal effort is required to update role definitions, existing implementation, database seed data, acceptance criteria and documentation.|
| Cost impact | None |
| Risk impact | Inconsistent references to Admin and Management could result in incorrect permission checks, outdated documentation or failed tests. Removing the Management role without updating all dependent components could also cause authorisation errors. These risks shall be mitigated by updating the requirements baseline, role definitions, database seed data, API policies and related tests together. |
| Recommendation | ACCEPT |
| Approved by | Thabang, Mutshidzi |
| Rationale | Admin and Management have equivalent access rights and functionality, so maintaining them as separate roles provides no meaningful security or operational benefit. Consolidating them reduces implementation and maintenance complexity while preserving the necessary distinction between normal staff and administrators. The revised model remains consistent with the existing requirements for request assignment, reporting, audit trails and lifecycle-history access. |
